# Timio v0.5.5 — Notification Automation & Fallback

This release continues the notification architecture without requiring real provider credentials.

## What changed

- Notification settings are now mounted behind authenticated `/me` routes.
- Added `GET /me/businesses/:id/notifications/logs`.
- New businesses receive default notification policies for booking, reminders and post-visit events.
- Dispatch now respects per-event notification settings.
- Each event can define its own ordered channel policy.
- Provider fallback is implemented: if an available provider rejects a message, Timio tries the next available channel.
- Logs preserve the attempted channel order and the final selected channel.
- Dashboard now exposes an `Автоматизация уведомлений` panel where owners can enable/disable events and choose channels.
- Existing real providers remain unchanged: Telegram, Twilio WhatsApp/SMS and Resend Email are only used when credentials/configuration are present.

## Intended future flow

`WhatsApp -> Telegram -> SMS -> Email` is now a supported policy shape, but a business can choose any order per event.

The architecture deliberately separates: event policy -> channel resolution -> provider delivery -> delivery log. This makes adding providers later possible without rewriting appointment/reminder logic.

## Important

No provider keys are required for this release. Without credentials, a real channel remains unavailable; Timio does not pretend that an external message was delivered.

## Validation

The source was syntax-inspected and the archive was integrity-checked. A full TypeScript build remains blocked by the existing environment's missing installed dependencies (`drizzle-orm`, `postgres`, `hono`, `@types/node`, etc.), so no full build-pass claim is made.
